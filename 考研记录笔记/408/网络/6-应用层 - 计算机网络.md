# 应用层【\*非重点；※重点】
---

不同的网络应用的应用进程之间，还需要有不同的通信规则，因此在运输层协议之上，还需要有应用层协议。

**应用层协议的具体定义**：
- 应用进程交换的报文类型(*如：请求报文和响应报文*)；
- 各种报文类型的语法(*如：报文中的各个字段及其详细描述*)；
- 字段的语义(*即：包含在字段中信息的含义*)；
- 进程何时、如何发送报文，以及对报文的响应的规则。

# 一、 网络应用模型

应用层的许多协议都是 **基于客户服务器方式**。即使 P2P 对等通信方式，实质上也是一种特殊的客户服务器方式。

## 1.1. 客户服务器(CS)模型

在客户/服务器(*C/S，Clien/Server*)模型中，**提出请求的称为客户**，**接收请求的称为服务器**。

**客户端**：可以是一台设备(*如：笔记本电脑*)或一个程序软件，它能够 **帮助客户访问服务器**；
**服务器**：是可以响应客户端服务请求的设备或程序，它存储着数据等信息，可以根据请求类型提供文件、数据库等内容。

![300](image/6-应用层%20-%20计算机网络/客户服务器模型示例.png)

**工作流程**：
1. **服务器** 在指定端口 **监听** 客户端的连接请求；
2. **客户端** 主动向服务器指定端口 **发出连接请求**；
3. **服务器** 收到来自客户端的连接请求后，会先 **进行一系列的准备工作**(*如：身份验证等*)，之后服务器就会和客户端 **建立连接**。
4. 连接建立后，**服务器与客户端进行双向通信**(*服务器可查找并响应客户端所请求的数据*)；
5. 通信结束，**双方断开连接**。

> **注意**：
>   1. C/S模型中，**客户之间不能直接通信，需要服务器中转**；
>   2. 服务器**总是保持开启状态**，被动响应客户端请求，因此C/S模型是**不对等的模型**；
>   3. 服务器事先不知道客户端的位置。

**优点**：安全(*服务器始终管理着访问控制权限*)，易于备份；
**缺点**：这类网络不可靠，**服务器的故障会影响到所有客户端**，建立和维护成本高。

**常见应用**：Web，文件传输协议(*FTP*)，远程登录，电子邮件。

## 1.2. 对等(P2P)模型

在对等(*P2P，Peer to Peer*)模型中，**每个节点既可以是客户端也可以是服务器，它可以请求服务也能提供服务**。

处于 P2P 网络中的一台设备也被称作一个 **对等节点**(*Peer Node*)。
**一个节点加入 P2P 网络后，可以向其他节点请求服务或提供服务**。

![300](image/6-应用层%20-%20计算机网络/P2P模型示例.png)

P2P是建立在 **客户/服务器模型** 的基础上的，它把单个服务器的负担分摊给了若干个客户节点。

**优点**：
1. 更容易维护，无须专门派人维护网络；
2. 整个网络 **并不依赖于一台机器**；
3. 建立网络 **不需要大量的硬件**；
4. 向多用户分发文件时，P2P可将任务分配给多个节点，用户可请求最近的节点，**通常比C/S模型更快**。

**缺点**：P2P网络不安全。

# 二、 域名系统(DNS)

**域名系统(*DNS，Domain Name System*)**：是互联网使用的命名系统，用于将人们便于记忆的、具有特定含义的主机名，转换为便于机器处理的IP地址。

**核心作用**：将域名解析为对应的IP地址。

**工作模式**：采用C/S模型，运行在UDP协议上，使用**53号端口**。

从概念上，DNS分为三部分：**层次域名空间、域名服务器和解析器**。

> **注意**：域名和IP地址**不是一一对应的关系**。
>   1. 一台主机连接到不同网络时，会拥有多个IP地址，即**多个IP地址可映射到同一个域名**；
>   2. 一台主机从多个域名管理机构获得域名时，可通过多个域名访问该主机，即**多个域名可映射到同一个IP地址**。

## 2.1. 层次域名空间

**域**：是名字空间中一个可被管理的划分。域可进一步划分为子域，子域继续细分，形成 **顶级域、二级域、三级域** 等层次结构。

每个域名由一系列标号组成，各标号之间用 `.` 分隔。

> **示例**：`www.baidu.com`
>   `com`：顶级域名
>   `baidu`：二级域名
>   `www`：三级域名
> **注意**：多个标号组成的完整域名总共不超过 `255` 个字符。

![400](image/6-应用层%20-%20计算机网络/域名空间树状结构示例.png)

**顶级域名分类**：

| 类型         | 说明       | 示例                                                  |
| :--------- | :------- | :-------------------------------------------------- |
| **国家顶级域名** | 按国家/地区分配 | `.cn`(*中国*)、`.us`(*美国*)、`.jp`(*日本*)                 |
| **通用顶级域名** | 按机构类型分配  | `.com`(*商业*)、`.org`(*组织*)、`.edu`(*教育*)、`.gov`(*政府*) |
| **基础结构域名** | 特殊用途     | `.arpa`(*用于反向域名解析*)                                 |

> **注意**：DNS既 **不规定** 一个域名需要包含多少个下级域名，也 **不规定** 每一级的域名代表什么含义。各级域名由其上一级的域名管理机构管理，最高级顶级域名由ICANN管理。

## 2.2. 域名服务器

域名服务器被设计为一种联机的 **分布式数据库系统**，采用 C/S 模型。

![500](image/6-应用层%20-%20计算机网络/DNS层次结构示例.png)

**种类**：
- **根域名服务器**(`.`)：顶级域名服务器的地址；
- **顶级域名服务器**(`.com`)：管理二级域名；
- **授权/权限域名服务器**(`baidu.com`)：负责一个区的映射；
- **本地域名服务器**：主机首先查询的服务器。

> **注意**：当授权域名服务器不能给出最终查询回答时，会告诉查询者下一步应查询哪个权限域名服务器。但 **一定能从某个授权服务器找到对应的IP地址**。

## 2.3. 域名解析过程

**域名解析**：将域名转换为 IP 地址的过程。当客户端需要进行域名解析时，会通过本机的DNS客户端构造一个DNS请求报文，并以UDP数据报的形式发送给本地域名服务器。

域名解析有两种方式：**递归查询和迭代查询**。
1. 主机向本地域名服务器的查询通常采用**递归查询**；
2. 本地域名服务器向其他域名服务器可采用**递归查询**或**迭代查询**。

### 2.3.1. 递归查询

![350](image/6-应用层%20-%20计算机网络/递归查询示例.png)

**基本过程**：本地域名服务器代替主机进行后续查询。若本地域名服务器不知道被查询域名的IP地址，则由它**替主机继续查询**，直到获得最终结果，再返回给主机。

**特点**：
- 主机 **只发送一次请求**；
- 本地域名服务器 **负担较重**，需完成全部查询工作；
- 对主机的查询过程是透明的。

### 2.3.2. 迭代查询

![350](image/6-应用层%20-%20计算机网络/迭代查询示例.png)

**基本过程**：本地域名服务器依次向各级域名服务器询问。当根域名服务器收到本地域名服务器的查询请求时，要么给出IP地址，要么告诉它“下一步应向哪个域名服务器查询”。

> **注意**：8个步骤共需要使用8个UDP用户数据报(*使用UDP减少开销*)的报文。

**特点**：
- 本地域名服务器需 **多次发送请求**；
- 各域名服务器 **负担较轻**，只返回自己知道的结果或下一级地址；
- 根域名服务器通常采用迭代查询。

### 2.3.3. 高速缓存(DNS缓存)

**目的**：
- 提高DNS查询效率(*缓存最近查询过的域名映射*)；
- 减轻根域名服务器的负荷；
- 减少互联网上的DNS查询报文数量。

**工作机制**：
- DNS服务器将查询结果**缓存**一段时间；
- 若缓存中有记录，本地域名服务器可直接返回结果，无需再次查询；
- 若缓存中无记录或**缓存过期**，则需重新查询。

# 三、 文件传输协议(FTP)

**文件传输协议**(*FTP，File Transfer Protocol*)：曾是互联网上使用最广泛的文件传送协议。

FTP 提供 **交互式访问**，允许客户指明文件的类型与格式(*如：指明是否使用 ASCII 码*)，并允许文件具有存取权限(*如：访问文件的用户必须经过授权，并输入有效地口令*)。

## 3.1. FTP概述

### 3.1.1. FTP的特点与功能

**特点**：
- 提供交互式访问；
- 允许客户端指定文件的类型与格式；
- 允许文件具有存取权限；
- 适合在异构网络中的任意计算机之间传送文件。

**功能**：
- 提供不同种类主机系统之间的文件传输能力；
- 以用户权限管理的方式提供用户对远程FTP服务器的文件管理能力；
- 以匿名FTP的方式提供公用文件共享的能力。

> **注意**：匿名FTP访问通常使用 `anonymous` 作为用户名。

### 3.1.2. FTP的传输模式

FTP支持两种传输模式：
- **ASCII模式**：用于文本文件；
- **Binary模式**：用于图像、声音等非文本文件。

### 3.1.3. FTP的服务器进程

**FTP使用客户/服务器方式**：一个FTP服务器进程可同时为多个客户进程提供服务。

**FTP服务器进程由两部分组成**：
- **主进程**：负责接受新的请求；
- **若干从属进程**：负责处理单个请求。

**主进程工作步骤**：
1. 打开熟知端口(*端口21*)，使客户进程能够连接上；
2. 等待客户进程发出连接请求；
3. 启动从属进程处理客户进程发来的请求(*主进程与从属进程并发执行，从属进程处理完毕后即终止*)；
4. 回到等待状态，继续接受其他客户进程发来的请求。

## 3.2. 控制连接与数据连接

FTP的客户和服务器之间要建立**两个并行的TCP连接**：**控制连接**和**数据连接**。

![555](image/6-应用层%20-%20计算机网络/控制连接和数据连接示例.png)

|        | 控制连接                                                                           | 数据连接              |
| :----- | :----------------------------------------------------------------------------- | :---------------- |
| **作用** | 将命令从客户端传输到服务器并传回服务器的应答                                                         | 用于传输文件            |
| **端口** | 21端口                                                                           | 20端口(*主动模式*)      |
| **特点** | 控制信息以7位ASCII格式传送；<br>控制连接在整个会话期间一直保持打开；<br>FTP的控制信息是 **带外(*Out-of-band*)传送** 的 | 每次文件传输时建立，传输完成后关闭 |

### 3.2.1. 连接的建立过程

1. 客户进程向服务器进程的**熟知端口21**发出连接请求，同时告知服务器自己的另一个端口号(*用于数据连接*)；
2. 服务器进程用**熟知端口20**与客户进程提供的端口号建立数据连接；
3. 由于使用了两个不同的端口号，数据连接与控制连接不会发生混乱。

> **注意**：控制连接**不用于传送文件**，实际传输文件的是**数据连接**。

### 3.2.2. 两种数据传输模式

| 模式 | 名称 | 工作方式 |
| :--- | :--- | :--- |
| **PORT模式(主动模式)** | 主动模式 | 服务器主动连接客户端的端口 |
| **PASV模式(被动模式)** | 被动模式 | 客户端主动连接服务器的端口 |

### 3.2.3. 使用两个连接的好处

1. 使协议更加简单和容易实现；
2. 在传输文件时，可利用控制连接对文件的传输进行控制(*如：用户可在文件传输过程中发送“请求中止服务”*)；
3. FTP的控制信息是 **带外传送** 的。

> **注意**：
>   1. FTP使用TCP可靠的传输服务；
>   2. FTP必须在整个会话期间 **保留用户的状态信息**(*服务器必须追踪用户在远程目录树上的当前位置*)。

# 四、 万维网(WWW)

## 4.1. WWW的概念与组成结构

**万维网**(*WWW，World Wide Web*)：是一个大规模的信息储藏所，简称 Web。

万维网用的链接方法能方便地从互联网上的一个站点访问另一个站点。

![300](image/6-应用层%20-%20计算机网络/万维网站点示例.png)


**概念**：
- **超文本(*Hypertext*)**：包含指向其他文档的链接的文本；
- **超媒体(*Hypermedia*)**：超文本的扩充，包含图形、图像、声音等多媒体信息；
- **万维网**：一个分布式的超媒体系统。

**工作模式**：万维网以 **客户/服务器** 方式工作。
- **浏览器**：用户主机上的万维网客户程序；
- **万维网服务器**：保存万维网文档的主机。

**统一资源定位符(*URL，Uniform Resource Locator*)**：用于标志万维网上的各种文档。

**URL的组成格式**：
$$协议://主机名[:端口]/路径$$

| 组成部分 | 说明 |
| :--- | :--- |
| **协议** | 如 http、ftp 等，后跟 `://` |
| **主机名** | 存放文档的主机域名或IP地址 |
| **端口** | 默认端口可省略(*HTTP默认80*) |
| **路径** | 文档在主机中的路径，可省略 |

## 4.2. HTTP协议

**超文本传输协议(*HTTP，Hypertext Transfer Protocol*)**：用于获取网络资源的应用层通信协议。
- 基于 **TCP** 连接进行可靠传输，服务器端口号为 **80**
- 采用 **客户/服务器** 模型
- HTTP协议本身是 **无连接** 的(*由TCP保证可靠传输*)
- HTTP协议是 **无状态** 的(*服务器不记得曾访问过的客户*)

### 4.2.1. HTTP的工作过程

![400](image/6-应用层%20-%20计算机网络/HTTP工作流程示例.png)

**基本流程**：
1. 服务器进程不断监听TCP端口80；
2. 浏览器与服务器建立TCP连接；
3. 浏览器向服务器发送HTTP请求报文；
4. 服务器返回HTTP响应报文；
5. 服务器完成任务后释放TCP连接(*或保持持续连接*)。

**用户浏览页面的两种方法**：
1. 在浏览器地址栏键入URL；
2. 在页面中点击超链接。

**访问一个URL的完整过程**：
1. 用户输入URL；
2. 浏览器解析域名，查询DNS缓存，若未命中则通过DNS获取IP地址；
3. 根据IP地址+端口号建立TCP连接；
4. TCP连接成功建立后，浏览器向服务器发送一条HTTP请求报文；
5. 服务器向浏览器发送一条HTTP响应报文；
6. 浏览器根据响应决定是否关闭TCP连接(*四次挥手*)；
7. 浏览器显示文档。

> **注意**：
>   1. HTTP 使用 **面向连接的TCP** 作为传输层协议，保证数据的可靠传输。
>   2. HTTP协议本身无连接，无需考虑数据传输过程中被丢弃后怎么重传，不需要建立HTTP连接。

### 4.2.2. HTTP的版本演进

**HTTP/1.0**：采用 **非持续连接**。
- 每个请求/响应需建立单独的TCP连接；
- 每个文档(包括图片等嵌入对象)都需要一次完整的TCP连接建立和释放；
- 耗时 = 文档传输时间 + 2 × RTT。

**HTTP/1.1**：采用 **持续连接**。
- 服务器发送响应后仍保持连接一段时间；
- 同一客户和服务器可继续在该连接上传送后续请求和响应；
- **非流水线方式**：客户收到前一个响应后才能发出下一个请求；
- **流水线方式**：客户可在收到响应前连续发送多个请求，提高效率。

### 4.2.3. HTTP报文结构

HTTP报文是面向文本的，每个字段都是ASCII码。

**请求报文**：开始行(*请求行*) + 首部行 + 空行 + 实体主体
**响应报文**：开始行(*状态行*) + 首部行 + 空行 + 实体主体

**常见请求方法**：

| 方法 | 作用 |
| :--- | :--- |
| **GET** | 从服务器获取资源 |
| **POST** | 向服务器发送数据以创建新资源 |
| **PUT** | 向服务器发送数据以更新现有资源 |
| **DELETE** | 从服务器删除指定资源 |
| **HEAD** | 类似于GET，但只返回响应头部 |

**常见状态码**：

| 状态码 | 含义 |
| :--- | :--- |
| **2xx** | 成功(*如200表示请求成功*) |
| **3xx** | 重定向(*如302表示资源被永久转移到其他URL*) |
| **4xx** | 客户差错(*如404表示请求的资源不存在*) |
| **5xx** | 服务器差错(*如500表示服务器内部错误*) |

**常见字段**：

| 字段 | 说明 |
| :--- | :--- |
| **Host** | 指明请求发送到的服务器主机名和端口号 |
| **Cookie** | 服务器生成的用户数据，用于识别会话状态 |
| **Connection** | 决定请求结束后是否关闭连接(*close* 或 *keep-alive*) |

# 五、 电子邮件

电子邮件系统是一种异步通信方式，用户在不同时间发送和接收邮件，无需双方同时在线。

## 5.1. 电子邮件系统的组成结构

基于WWW的电子邮件(*如Gmail*)：
- 用户浏览器与邮件服务器之间用 **HTTP** 发送或接收邮件；
- 不同邮件服务器之间传送用 **SMTP**。

**三个组成部分**：
- **用户代理(*UA*)**：用户与电子邮件系统的接口(*如：Outlook，Foxmail*)；
- **邮件服务器**：用来发送和接收邮件；
- **邮件发送协议**：SMTP(*类似于Push*) 和 **读取协议**：POP3/IMAP(*类似于Pull*)。

## 5.2. 电子邮件格式与MIME

电子邮件 = 信封 + 内容

内容 = 首部 (*RFC822 规定*) + 主体 (*用户自用撰写*)

**首部的关键字**：
- **From**：发件人地址(*必须*)，由邮件系统自动填入；
- **To**：收件人地址(*必须*)，格式为 `用户名@域名`；
- **Subject**：邮件主题(*可选*)。

**多用途网络邮件扩充(*MIME*)**：
- SMTP只能传送一定长度的ASCII码邮件，且**无法传送可执行文件及其他二进制对象**，因此提出MIME；
- MIME继续使用SMTP的格式，增加了邮件主体的结构，定义了传送非ASCII码的编码规则(*如Base64、QP编码*)；
- 支持**附件、非ASCII字符、多媒体内容**。

## 5.3. 发送协议和读取协议

### 5.3.1. SMTP

**定义**：一种提供可靠且有效的电子邮件传输协议。

**特点**：
- 使用C/S方式；
- 使用TCP连接，端口号 **25**；
- 只支持传输 **7比特ASCII码** 内容；
- 使用明文传输命令和响应。

**通信过程**：
1. 连接建立；
2. 邮件传送；
3. 连接释放。

> **注意**：SMTP的加密版本为 **SMTPS**(端口465)。

### 5.3.2. POP3

**定义**：一种非常简单但功能有限的邮件读取协议。

**特点**：
- 使用C/S方式；
- 使用TCP连接，端口号 **110**；
- POP3协议**使用明文传输密码**，不对密码加密；
- 将邮件从服务器下载到本地后，**通常删除服务器上的邮件**。

**两种工作模式**：
- 下载并保留(*服务器保留副本*)；
- 下载并删除(*服务器删除副本*)。

> **注意**：POP3是**拉取协议**(*Pull*)，用户主动从服务器下载邮件。

### 5.3.3. IMAP

**定义**：因特网报文存取协议(*Internet Message Access Protocol*)。

**特点**：
- 使用C/S方式，使用TCP连接，端口号 **143**；
- 为用户提供了联机命令：创建文件夹、在不同文件夹间移动邮件、在远程文件夹中查询邮件；
- IMAP服务器**维护会话用户的状态信息**；
- 允许用户代理**只获取报文的某些部分**(*如只获取邮件首部*)，适合低带宽情况；
- 邮件**保存在服务器端**，多设备可同步访问。

> **注意**：IMAP是**拉取协议**，但比POP3功能更强大，支持服务器端邮件管理。
