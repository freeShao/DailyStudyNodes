# 一、 传输层提供的服务

传输层是 **端系统(*主机*)** 才有的层次，路由器最多能够到达网络层。

**传输层**：为运行在不同主机上的[进程](<2-进程管理 - 操作系统.md# 一、 进程>)之间提供 **逻辑通信**；
**网络层**：提供 **主机之间** 的逻辑通信。

> **注意**：只有主机的协议栈才有传输层和应用层，路由器最多只到网络层。

## 1.1. 传输层的功能

### 1.1.1. 端到端的逻辑通信

传输层为应用进程之间提供 **端到端** 的逻辑通信服务。

![555](image/5-传输层%20-%20计算机网络/应用程序间的逻辑通信示例.png)

**逻辑通信的含义**：从应用层的视角看，只要把报文交给传输层，传输层就能把它送到对端的传输层，好像有一条水平方向的直接通路。但实际上数据是沿着网络层、数据链路层、物理层逐层向下再向上的。

### 1.1.2. 复用与分用

- **复用(*Multiplexing*)**：发送方不同的应用进程可以使用 **同一个传输层协议** 来发送数据；
- **分用(*Demultiplexing*)**：接收方的传输层收到数据后，剥去报文首部，根据端口号将数据 **正确交付给对应的应用进程**。

> 复用和分用是传输层最核心的功能之一，依赖于 **端口号** 来区分不同的进程。

### 1.1.3. 差错检测

- **网络层**：只检验IP数据报的 **首部**，不检查数据部分；
- **传输层**：需要对收到的 **整个报文**(首部+数据)进行差错检测。

> **注意**：UDP的校验是可选的，TCP的校验是强制的。校验出错的报文直接丢弃。

### 1.1.4. 提供两种不同的传输协议

传输层向应用层提供两种服务模型：

| 协议 | 服务类型 | 特点 |
| :--- | :--- | :--- |
| **TCP** | 面向连接 | 可靠、有流量控制和拥塞控制、开销大 |
| **UDP** | 无连接 | 不可靠、无拥塞控制、开销小、实时性好 |

> **注意**：
>   1. 使用TCP时，尽管底层网络仅提供“尽最大努力”的服务，TCP通过确认、重传等机制，在逻辑上为应用层提供了一条 **全双工的可靠信道**；
>   2. 使用UDP时，传输层提供的仍然是 **不可靠信道**，可靠性需要由应用层自己保证。

### 1.1.5. 端口号分类

| 类型       | 范围            | 说明                                         |
| :------- | :------------ | :----------------------------------------- |
| **熟知端口** | 0 ~ 1023      | 固定分配给常用服务（如 HTTP=80，FTP=21，DNS=53，SMTP=25） |
| **登记端口** | 1024 ~ 49151  | 需登记，避免重复                                   |
| **短暂端口** | 49152 ~ 65535 | 客户端临时使用                                    |

# 二、 UDP协议

## 2.1. UDP概述

**UDP协议**：只在IP的数据报服务至上增加了很少的功能(*即复用、分用以及差错检测*)。

### 2.1.1. UDP的主要特点

| 特点                                             | 说明                                        |
| :--------------------------------------------- | :---------------------------------------- |
| **无连接**                                        | 发送数据前不需要建立连接，减少了开销和时延                     |
| **不可靠交付**                                      | 尽最大努力交付，不保证可靠交付                           |
| **面向报文**                                       | 对应用层报文**不拆分、不合并**，添加首部后直接交付IP层，一次发送一个完整报文 |
| **无[拥塞控制](<4-网络层 - 计算机网络.md### 1.2.5. 拥塞控制>)** | 网络拥塞不会降低发送速率，适合实时应用(*如IP电话、视频会议*)         |
| **支持多种通信方式**                                   | 支持一对一、一对多、多对一、多对多交互通信                     |
| **首部开销小**                                      | 首部仅8字节(*TCP为20字节*)                        |
> **注意**：UDP对应用层交下来的报文既不合并，也不拆分，即：应用层交给UDP多长的报文，**UDP就照样发送(*一次发送一个报文*)**。

![555](image/5-传输层%20-%20计算机网络/UDP协议报文向下传输示例.png)

> **注意**：
>   报文太长，UDP把报文交给IP层后，会导致分片；
>   报文太短，UDP把报文交给IP层后，会使IP数据报的首部相对长度太大；
>   **二者都会降低IP层的效率**。

### 2.1.2. UDP的通信和端口号的关系

UDP通过 **端口号** 实现进程间的通信。以下图为例：

![555](image/5-传输层%20-%20计算机网络/UDP通信和端口号关系示例.png)

主机H1中有三个应用进程，分别要与主机H2中的两个应用进程通信：
- `P1 -> P4`
- `P2 -> P4`
- `P3 -> P5`

H1为这三个进程分别指派了端口号：`a`、`b`、`c`。H2中P4和P5的端口号分别为 `x` 和 `y`。

**UDP用户数据报中的关键地址信息**：

| 发送方 | 源端口 | 目的端口 | 对应关系 |
| :--- | :--- | :--- | :--- |
| P1 | a | x | P1 -> P4 |
| P2 | b | x | P2 -> P4 |
| P3 | c | y | P3 -> P5 |

> **注意**：
> 1. 图中运输层之间的虚线 **不是一条连接**，仅表示逻辑通信关系；
> 2. 端口具有缓存功能，可暂存收到的数据；
> 3. **UDP通信是不可靠的**：报文可能丢失，也不保证按序到达。

## 2.2. UDP首部格式与检验

### 2.2.1. 首部格式

用户数据报 UDP 有两个字段：**数据字段和首部字段**。

![555](image/5-传输层%20-%20计算机网络/UDP首部格式示例.png)

首部字段只有 *8字节*，由四个字段组成，每个字段长度都是两个字节。

| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| **源端口** | 2B | 发送端端口号，不需要对方回信时可用全0 |
| **目的端口** | 2B | 接收端端口号，**终点交付时必须使用** |
| **长度** | 2B | UDP数据报的总长度(*首部+数据*)，最小值为8 |
| **校验和** | 2B | 检测UDP数据报在传输中是否出错，出错则丢弃 |

> **注意**：若接收方UDP发现目的端口号不存在，则丢弃该报文，并由ICMP发送“端口不可达”差错报文。

### 2.2.2. UDP检验和

UDP在计算检验和时，要在 UDP 用户数据报之前增加 **12字节的伪首部**。

**伪首部**：不是UDP数据报真正的首部，仅在计算检验和时临时添加，既不向下传送也不向上递交。

**伪首部格式**(*12字节*)：

| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| 源IP地址 | 4B | 发送方IP地址 |
| 目的IP地址 | 4B | 接收方IP地址 |
| 全0 | 1B | 固定为0 |
| 协议号 | 1B | 对于UDP，固定为 **17** |
| UDP长度 | 2B | UDP数据报的长度(*与UDP首部中的长度字段一致*) |

**UDP校验与[IP校验](<4-网络层 - 计算机网络.md#### (十二) 首部检验和>)的区别**：

| 对比项 | IP首部检验和 | UDP检验和 |
| :--- | :--- | :--- |
| **校验范围** | 仅IP首部 | **伪首部 + UDP首部 + 数据部分** |
| **校验字段** | 首部校验和 | UDP校验和 |

**发送方计算步骤**：
1. 将校验和字段 **置为全0**；
2. 将伪首部以及UDP数据报看作由多个 **16位字** 串接而成；
3. 若数据部分为 **奇数个字节**，则**末尾补一个全0字节**(*仅用于计算，不发送*)；
4. 按 **二进制反码** 计算出所有16位字的和；
5. 将所得和的 **反码** 写入校验和字段。

![555](image/5-传输层%20-%20计算机网络/UDP检验和计算示例.png)

**接收方验证步骤**：
1. 将收到的UDP数据报连同伪首部(*以及可能的填充字节*)一起，按二进制反码求所有16位字的和；
2. 若结果为 **全1**，则说明无差错；
3. 若结果 **不为全1**，则说明数据报出错，**丢弃**该数据报(*也可交付上层，但附上差错警告*)。

> **注意**：
> 1. UDP校验和校验出的UDP数据报是错误的，可以丢弃，也可以交付给上层，**但是要附上错误报告**。
> 2. UDP检验和字段的使用时可选的，**若源主机不想计算检验和，则检验和字段应为0**。

# 三、 TCP协议

## 3.1. TCP特点

TCP是 **面向连接** 的传输层协议。

TCP连接是一条 **[虚电路](<2-物理层 - 计算机网络.md## 2.4. 数据报与虚电路>)(*逻辑连接*)**，不是一条真正的物理连接。

### 3.1.1. TCP的主要特点

**面向连接**：TCP在传输数据之前，通信双方必须先建立一条连接。数据传送结束后，再释放连接。这种连接是一条**虚连接**，而不是物理连接。

**点对点**：每条TCP连接只能有两个端点，不支持多播和广播。TCP只能实现一对一的两端通信。

**可靠交付**：TCP提供可靠的数据传输服务。通过确认机制、超时重传、序号管理等方式，保证数据无差错、不丢失、不重复，并且按序到达。

**全双工通信**：TCP通信的双方可以同时发送和接收数据。因此，TCP连接的每一端都设有发送缓存和接收缓存，分别用于暂存待发送的数据和已收到的数据。

**面向字节流**：TCP将应用层交下来的数据视为一连串无结构的字节流。TCP不关心应用层报文的边界，也不对数据进行合并或拆分，而是按照实际收到的字节数进行传输。

**流量控制**：TCP通过滑动窗口机制进行流量控制，使发送方的发送速率不超过接收方的接收能力，避免接收方因处理不及时而丢失数据。

**拥塞控制**：TCP能够感知网络的拥塞状况，并通过慢开始、拥塞避免、快重传和快恢复等算法，动态调整发送速率，防止网络过载。

### 3.1.2. TCP连接的端点

每条TCP连接只能有两个端点。TCP连接的端点称为 **套接字(*socket*)**，也称为插口。
套接字由IP地址和端口号共同构成：
$$套接字 = (IP地址 : 端口号)$$

一条完整的TCP连接由两个套接字唯一标识：
$$TCP连接 = \{ socket1, socket2 \} = \{ (IP1:port1), (IP2:port2) \}$$

> **注意**：TCP连接**由两个端点唯一确定**，即使IP地址或端口号发生变化，连接也会随之改变。

## 3.2. TCP报文段(TCP段)

一个TCP报文段=首部+数据部分
首部的前20个字节是固定的
后面有4n字节是根据需要而增加的选项
TCP首部的最小字节是20字节。

![500](image/5-传输层%20-%20计算机网络/TCP报文段示例.png)

| 字段                    | 长度  | 说明                                    |
| :-------------------- | :-- | :------------------------------------ |
| **源端口**               | 2B  | 发送端端口号                                |
| **目的端口**              | 2B  | 接收端端口号                                |
| **序号**                | 4B  | 本报文段所发送数据的**第一个字节的序号**                |
| **确认号**               | 4B  | 期望收到的**下一个字节的序号**(*累计确认*)             |
| **数据偏移**(*首部长度*)      | 4位  | TCP首部长度，以4B为单位，最小5(*20B*)，最大15(*60B*) |
| **保留**                | 6位  | 保留为今后使用，置0                            |
| **URG**(*紧急位*)        | 1位  | 紧急指针有效                                |
| **ACK**(*确认位*)        | 1位  | 确认号有效(*连接建立后所有报文段必须置1*)               |
| **PSH**(*推送位*)        | 1位  | 推送操作，尽快交付应用层                          |
| **RST**(*复位位，Reset*)  | 1位  | 复位连接(*出现严重差错时*)                       |
| **SYN**(*同步位*)        | 1位  | 同步序号，用于连接建立                           |
| **FIN**(*终止位，Finish*) | 1位  | 终止连接，释放连接                             |
| **窗口**                | 2B  | 接收窗口大小(*rwnd*)，用于流量控制                 |
| **检验和**               | 2B  | 校验首部+数据(*含伪首部*)                       |
| **紧急指针**              | 2B  | URG=1时有效，指出紧急数据末尾位置                   |
| **选项**                | 可变  | 如MSS、窗口扩大因子、时间戳等                      |
| **填充**                | 可变  | 保证首部是4B的整数倍                           |

## 3.3. TCP连接管理

TCP是面向连接的协议，因此每条TCP链接都包含三个阶段：**建立连接、数据传送和连接释放**。
**TCP连接管理的目标**：确保连接的建立与释放能够正常、可靠地进行。

TCP连接的建立采用 **客户/服务器模式**。主动发起连接建立的应用进程称为 **客户**(*Client*)，被动等待连接请求的应用进程称为 **服务器**(*Server*)。

TCP报文段是交给IP层传送的，但IP层只能提供 “*尽最大努力*” 服务，即不可靠的服务。

数据链路层中关于 [流量控制与可靠传输的原理](<3-数据链路层 - 计算机网络.md# 二、 流量控制与可靠传输机制>) 机制可以应用到TCP协议中。

### 3.3.1. TCP连接的建立

TCP建立连接的过程叫做 **握手**，握手需要在 **客户和服务器之间** 交换三个TCP报文段。

假设 *主机A* 运行的是TCP客户程序，而 *主机B* 运行TCP服务器程序，**最初两端的TCP进程都处于 `CLOSED` 状态**。

![400](image/5-传输层%20-%20计算机网络/用“三次握手”建立TCP连接示例.png)
> **注意**：在连接建立前，服务器完成一些准备工作后进入 `LISTEN` (*收听*)状态，等待客户的连接请求。

![555](image/5-传输层%20-%20计算机网络/报文段示例.png)

**第一步(*客户 -> 服务器*)**：客户向服务器发送 **连接请求报文段**。
- 报文段首部中的 **SYN = 1**，表示这是一个连接请求；
- 客户选择一个 **初始序号 seq = x** (*x 通常是随机生成的*)，客户下一次发送的报文段序号 **seq = x+1**；
- 该报文段 **不能携带数据**，但 **消耗一个序号**；
- 发送后，客户进入 `SYN-SENT` (*同步已发送*)状态。

**第二步(*服务器 -> 客户*)**：服务器收到连接请求报文段后，若同意建立连接，则向客户返回 **确认报文段**。
- 报文段首部中的 **SYN = 1**，**ACK = 1**，表示这是一个连接接受确认；
- 确认号 **ack = x + 1**，表示期望收到客户的下一个字节序号；
- 服务器选择自己的 **初始序号 seq = y**；
- 该报文段 **不能携带数据**，但 **消耗一个序号**；
- 发送后，服务器进入 `SYN-RCVD` (*同步收到*)状态。

**第三步(*客户 -> 服务器*)**：客户收到服务器的确认报文段后，向服务器发送 **确认报文段**。
- 报文段首部中的 **ACK = 1**，表示这是一个确认；
- 序号 **seq = x + 1** (*消耗了第一个序号后，下一个待发送的字节序号*)；
- 确认号 **ack = y + 1**，表示客户期望收到服务器的下一个字节序号；
- **该报文段可以携带数据**。若携带数据，则消耗序号；若 **不携带数据，则不消耗序号**；
- 发送后，客户进入 `ESTABLISHED` (*已建立连接*)状态。

服务器收到该确认报文段后，也进入 `ESTABLISHED` 状态。此时，TCP连接正式建立，双方可以开始传输数据。

> **注意**：
>   1. SYN报文段(*SYN=1的报文段*)即使不携带数据，也要 **消耗一个序号**；
>   2. 第三次握手的ACK报文段若**不携带数据，则不消耗序号**；
>   3. 仅在第一次握手的报文段中，ACK=0，因为此时尚未收到任何报文段；
>   4. 为什么需要**三次握手**？
>      主要是为了防止**已失效的连接请求报文段**突然又传到服务器，从而产生错误连接。如果只有两次握手，服务器收到一个过期的SYN请求后就会建立连接，造成资源浪费。
>   5. **若两台主机的两个进程所对应的端口之间已经建立一条TCP连接，则之后建立的连接都会被终止**。

### 3.3.2. TCP连接的释放

TCP连接的释放过程通常称为 *四次挥手*。

**前提**：通信双方均处于 `ESTABLISHED` 状态。现假设 **客户** 主动发起连接释放。

![400](image/5-传输层%20-%20计算机网络/用“四次挥手”释放TCP连接示例.png)
> **注意**：数据传输结束后，通信的双方都可释放连接。

![555](image/5-传输层%20-%20计算机网络/报文段示例.png)

**第一步(*客户 -> 服务器*)**：客户发送 **连接释放报文段**。
- 报文段首部中的 **FIN = 1**，表示此报文段发送方的数据已发送完毕，要求释放连接；
- 序号 **seq = u** (*u 等于已传送过的数据的最后一个字节的序号加1*)；
- 该报文段**不能携带数据**，但**消耗一个序号**；
- 发送后，客户进入 `FIN-WAIT-1` (*终止等待1*)状态，等待服务器的确认。
> **注意**：客户发送FIN，表示 “*我不再发送用户数据了*”，但TCP协议栈仍然可以发送ACK等控制报文来配合对方完成关闭。因此第四步中发送ACK是正常行为。

**第二步(*服务器 -> 客户*)**：服务器收到连接释放报文段后，发送 **确认报文段**。
- 报文段首部中的 **ACK = 1**，确认号 **ack = u + 1**；
- 自己的序号 **seq = v** (*v 等于已传送过的数据的最后一个字节的序号加1*)；
- 发送后，服务器进入 `CLOSE-WAIT` (*关闭等待*)状态。
此时，从客户到服务器这个方向的连接已释放，TCP连接进入 **半关闭** 状态。客户不再向服务器发送数据，但服务器若还有数据要发送，客户仍需接收。
客户收到确认后，进入 `FIN-WAIT-2` (*终止等待2*)状态，等待服务器发送连接释放报文段。
> **注意**：服务器进入 `CLOSE-WAIT` 状态后，**必须由应用程序主动调用 `close()`**，才能触发第三步发送FIN。如果应用程序不调用 `close()`，连接将一直停留在 `CLOSE-WAIT` 状态，无法完成释放。

**第三步(*服务器 -> 客户*)**：服务器数据发送完毕后，发送 **连接释放报文段**。
- 报文段首部中的 **FIN = 1**，**ACK = 1** (*确认号仍为 ack = u + 1*)；
- 自己的序号 **seq = w** (*在半关闭期间可能已发送了额外数据*)；
- 发送后，服务器进入 `LAST-ACK` (*最后确认*)状态，等待客户的确认。

**第四步(*客户 -> 服务器*)**：客户收到服务器的连接释放报文段后，发送 **确认报文段**。
- 报文段首部中的 **ACK = 1**，确认号 **ack = w + 1**；
- 自己的序号 **seq = u + 1** (*FIN报文段消耗了一个序号*)；
- 发送后，客户进入 `TIME-WAIT` (*时间等待*)状态。
此时，TCP连接尚未彻底释放。客户需等待 **2MSL** (*最长报文段寿命的两倍*)时间后，才进入 `CLOSED` 状态。

服务器收到客户的确认后，立即进入 `CLOSED` 状态。

> **注意**：
>   1. 主动关闭方在发送最后一个ACK后，需等待 **2MSL**，确保对方能收到该ACK(*若丢失，对方会重发FIN，本方仍能响应*)；
>   2. 等待2MSL还能防止 **已失效的连接请求报文段** 出现在新连接中；
>   3. 通常由客户端发起主动关闭，但服务器也可主动关闭；
>   4. FIN报文段即使不携带数据，也 **消耗一个序号**；
>   5. 第一步时客户发送FIN，表示 **不再发送用户数据**，但TCP协议栈仍可发送ACK等控制报文。因此第四步发送ACK是正常的协议行为，不违反“已释放连接”的语义；
>   6. 服务器在 `CLOSE-WAIT` 状态时，**必须由应用程序主动调用close()** 才能继续释放流程，否则连接将一直残留。

## 3.4. TCP可靠传输

TCP提供的可靠数据传输保证接收方进程从缓存区读出的字节流与发送方发出的字节流完全一样。
TCP使用检验(*与UDP一致*)，序号，确认，重传来达到这个目的。

### 3.4.1. 序号

![400](image/5-传输层%20-%20计算机网络/TCP段划分示例.png)

TCP将应用层交下来的数据视为 **无结构的字节流**，并为字节流中的 **每一个字节** 都分配一个序号。

- 每个报文段中的**序号字段**，表示该报文段所发送数据的 **第一个字节的序号**；
- 序号字段占 **4字节(32位)**，取值范围 `0 ~ 2^32 - 1`，序号达到最大值后回到0；
- 初始序号(*ISN*)在连接建立时 **随机选择**，而不是从0开始。

> **示例**：若某报文段序号为301，携带数据100字节，则该报文段数据部分为字节301~400。下一个报文段的序号应为401。

### 3.4.2. 确认

TCP采用**累计确认**机制。

- **确认号**：表示 **期望收到对方下一个报文段的第一个数据字节的序号**；
- 确认号 = 已正确收到的最后一个字节序号 + 1；
- 确认号之前的 **所有字节** 均已按序正确接收。

> **示例**：若接收方正确收到序号501~700的200字节数据，则确认号为701，表示序号700及之前的数据均已收到。

**确认的特点**：
- **捎带确认**：接收方在发送数据时，可将确认信息附带在数据报文段中一起发送，减少单独发送确认的开销；
- TCP规定，接收方 **不能对收到的数据报文段进行否认**，只能发送确认(*正向确认*)；
- 若接收方收到失序报文段，则发送 **重复确认**(*冗余ACK*)，确认已收到的最后一个按序字节。

> **注意**：TCP的确认号是 **期望收到的下一个字节序号**，而不是已收到的最后一个字节序号。

### 3.4.3. 重传

#### （一） 超时重传

发送方每发送一个报文段，就为该报文段设置一个**超时计时器**。

- 若在计时器**超时前**收到确认，则撤销计时器；
- 若计时器**超时**仍未收到确认，则**重传**该报文段。

**超时时间**(*RTO，Retransmission Timeout*)的设定：
- RTO应略大于 **[往返时间](<1-计算机网络体系结构 - 计算机网络.md### 1.3.6. 往返时延(RTT)>)(RTT)**；
- RTT通过 **加权移动平均** 动态估计；
- 若RTO设置过短，会导致不必要的重传；若过长，则降低传输效率。

#### （二） 冗余ACK(*冗余确认*)

当接收方收到一个**失序报文段**时(即收到的报文段序号大于期望的序号)，会立即发送一个**重复的ACK**，确认**已收到的最后一个按序字节**。

- 发送方收到**3个重复ACK**时，认为该报文段已丢失，**立即重传**该报文段——即 **快重传**；
- 快重传 **无需等待超时**，可更快恢复丢失的报文段。

> **注意**：冗余ACK的意义在于 **提前通知发送方有报文段丢失**，避免因等待超时而降低传输效率。

## 3.5. TCP流量控制

流量控制的功能是确保发送方的发送速率不会过快，以便让接收方能够及时处理。因此，可以说流量控制是一种 **速度匹配服务**，它匹配发送方的发送速率和接收方的读取速率。

TCP利用 **[滑动窗口](<3-数据链路层 - 计算机网络.md### 2.1.2. 滑动窗口流量控制>)机制** 来实现流量控制。

**拥塞窗口**(*cwnd*)：发送方根据当前网络拥塞程度估计而确认的窗口值；
**接收窗口**(*rwnd*)：接收方根据自己接收缓存的大小，动态地调整发送方的窗口大小。

### 3.5.1. 滑动窗口流量控制的基本原理

- 接收方在**确认报文段**中通过 **窗口字段(*rwnd*)** 通告自己的 **接收窗口大小**；
- 接收窗口大小 = 接收方的可用缓存空间；
- 发送方的 **发送窗口** 大小不能超过接收方通告的 **接收窗口** 大小。

![555](image/5-传输层%20-%20计算机网络/利用滑动窗口进行流量控制示例.png)
> **上图中，接收方的 主机B 进行了三次流量控制**：
>   1. 把接收窗口减少到 `rwnd=300`；
>   2. 又减到 `rwnd=100`；
>   3. 最后减到 `rwnd=0`，即不允许发送方再发送数据。
>**发送方暂停发送的状态将持续到 主机B 重新发出一个新的窗口值为止**。

### 3.5.2. 滑动窗口的动态变化

接收方可根据自身缓存情况，动态调整窗口大小，并通过确认报文段告知发送方：
- **rwnd > 0**：发送方可在窗口范围内继续发送数据；
- **rwnd = 0**：发送方停止发送数据，进入 **零窗口状态**；
- 发送方启动 **持续计时器**，定期发送 **零窗口探测报文**，询问接收方窗口是否已恢复；
- 接收方在确认中通告新的 rwnd 值，发送方恢复发送。

> **注意**：持续计时器的作用是防止“死锁”——若接收方发送的非零窗口通告丢失，发送方在等待接收方通知，接收方在等待发送方发送数据，双方就会永远等待下去。

### 3.5.3. TCP流量控制与数据链路层滑动窗口的区别

| 对比项         | 数据链路层滑动窗口 | TCP流量控制滑动窗口        |
| :---------- | :-------- | :----------------- |
| **窗口大小**    | 固定        | **动态变化**(*由接收方通告*) |
| **窗口调整依据**  | 协议固定      | 接收方缓存余量            |
| **发送方窗口上限** | 固定值       | min(rwnd, cwnd)    |

> **例题**：
> ![555](image/5-传输层%20-%20计算机网络/流量控制的滑动窗口例题.png)
> 第三个段的起始序号是1000，由于三个段是连续的，因此其字节分配如下：
> 500~699 - 字节1；700~999 - 字节2；1000~1399 - 字节3。
> 由于只接收1和3段，2段未知，此时就需要重发2段，而3段处于 **失序到达**，不可推进累计确认号前进。所以发送给甲的确认号是700(*按序最后收到的字节序号+1*)。(C)
 
## 3.6. TCP拥塞控制

网络层中 [拥塞控制](<4-网络层 - 计算机网络.md### 1.2.5. 拥塞控制>) 概念。
判断网络是否进入拥塞状态的方法是，观察网络的吞吐量与网络负载的关系。
- 随着负载增加，吞吐量明显小于正常的吞吐量：**轻度拥塞**；
- 吞吐量随网络负载的增大而下降：**拥塞状态**。

TCP进行拥塞控制的算法有四种：慢开始和拥塞避免、快重传和快恢复。
**假定**：
1. 数据是单方向传送的，对方只传送确认报文；
2. 接收方总有足够大的缓存空间，因而发送窗口的大小由网络的拥塞程度来决定。

### 3.6.1. 慢开始和拥塞避免

发送方维持一个状态变量 **拥塞窗口 cwnd**，拥塞窗口的大小取决于网络的拥塞程度。

发送方控制拥塞窗口的原则是：
- 只要网络没有出现拥塞，拥塞窗口就可以再增大一些；
- 但只要网络出现拥塞或有可能出现拥塞，就必须把拥塞窗口减小一些，以减少注入到网络中的分组数。

#### （一） 慢开始算法

**基本原理**：发送方在开始发送时，不清楚网络的负载情况，因此不宜立即将大量数据注入网络。慢开始算法使拥塞窗口(*cwnd*)从1开始，**逐步增大**，探测网络的承载能力。

![300](image/5-传输层%20-%20计算机网络/慢开始示例.png)

**具体过程**：
1. 初始化 cwnd = 1，慢开始门限 ssthresh 为一个较大的值；
	- 当 `cwnd<ssthresh` 时，使用慢开始算法;
	- 当 `cwnd>ssthresh` 时，停用慢开始，改用 **拥塞避免算法**；
	- 当 `cwnd=ssthresh` 时，慢开始和拥塞避免都可使用。
2. 每收到一个对**新报文段**的确认，cwnd += 1；
3. 每经过一个RTT，cwnd **翻倍增长**(*指数增长*)。

当cwnd<ssthresh时，使用上述的慢开始算法。

> **注意**：发送方每收到一个确认就调整拥塞窗口大小。
> “慢”指的是开始只发送一个报文段，而不代表 cwnd 的增长速率慢。

#### （二） 拥塞避免算法

**基本原理**：当cwnd达到ssthresh后，为避免网络拥塞，让cwnd**缓慢增长**。

**具体过程**：
- 每经过一个RTT，cwnd += 1（*线性增长*）；
- 增长速率变慢，使网络不易进入拥塞状态。

> **注意**：拥塞避免只是让cwnd增长得慢一些，不能完全避免拥塞。当网络真的发生拥塞时，仍会导致超时。

#### （三） 网络拥塞的处理

当发送方**检测到超时**时，说明网络已发生拥塞，此时：
1. 将 `ssthresh = cwnd / 2`；
2. 将 **cwnd = 1**；
3. 重新进入**慢开始**阶段。

> **注意**：超时是判断网络拥塞的最强信号。一旦发生超时，发送方会大幅降低发送速率，再通过慢开始逐步恢复。

**示例**：假设TCP的发送窗口等于拥塞窗口，连接建立后 cwnd = 1，ssthresh = 16。
![555](image/5-传输层%20-%20计算机网络/网络拥塞处理示例.png)
**过程分析**：
1. **慢开始阶段(①~②)**：cwnd 从1开始，每经过一个RTT翻倍增长，依次为1、2、4、8、16。当 cwnd = ssthresh = 16 时，转入拥塞避免。
2. **拥塞避免阶段(②~③)**：cwnd 从16开始线性增长，每经过一个RTT增加1，依次为17、18、……、24。
3. **超时发生(③)**：当 cwnd = 24 时，网络发生拥塞，发送方检测到超时。此时：
    - ssthresh = cwnd / 2 = 12
    - cwnd = 1
    - 重新进入慢开始
4. **第二次慢开始阶段(③~④)**：cwnd 再次从1开始指数增长，到 cwnd = 12 时转入拥塞避免。
5. **第二次拥塞避免阶段(④~⑤)**：cwnd 从12开始线性增长，到 cwnd = 16 时，发送方收到3个重复ACK（*3-ACK*），触发快重传和快恢复，而不是超时。

> **区别**：
>   **超时** -> 网络拥塞严重 -> ssthresh减半，cwnd归1，进入慢开始；
>   **3个重复ACK** -> 个别报文段丢失，网络未严重拥塞 -> 执行快重传和快恢复，不进入慢开始。

### 3.6.2. 快重传和快恢复

#### （一） 快重传

**基本思想**：当发送方收到 **3个重复的ACK** 时，认为该报文段已丢失，**立即重传**，而不必等待超时计时器超时。

**工作原理**：
1. 接收方每收到一个**失序报文段**，立即发送**重复ACK**（*确认已收到的最后一个按序字节*）；
2. 发送方收到 **3个重复ACK** 后，立即重传丢失的报文段。

> **注意**：快重传让发送方**不必等待超时**就能重传丢失报文段，从而提高了网络的吞吐量。

#### （二） 快恢复

**基本思想**：快重传之后，发送方认为网络并未出现严重拥塞（*因为仍能收到ACK*），因此**不启动慢开始**，而是直接进入**拥塞避免**。

**执行过程**：
1. `ssthresh = cwnd / 2`；
2. `cwnd = ssthresh`；
3. 直接进入**拥塞避免**阶段。

> **注意**：
>   1. 快恢复与超时后的处理不同——超时触发慢开始，快恢复不触发慢开始；
>   2. 快重传+快恢复避免了不必要的慢开始，提高了网络利用率。
